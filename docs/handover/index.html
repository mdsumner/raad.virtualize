Production handover

The research team indexes Southern Ocean and Antarctic array data and publishes it in cloud-readable form on source.coop. This page opens with the brief of 2026-11-23: which products production can take first, what is in place for them, and what to weigh. Then it shows how the pieces sit, the proposed production shape, and what is open. Anything marked proposal is not done.

What is in place

  • Engine tag. raad.virtualize v0.1.0, the version a product repo pins. Its release notes state the byte-reference table, the published layout, the catalog columns, the config interface and the runtime image by digest.
  • Publish gate. verify writes verify.json, which is published with the store, and publish refuses without a pass that matches the store as built. A failed verify blocks a publish run on its own, and no override exists.
  • Freshness. The Datasets page gives each store's owner, update model, upstream cadence and where its bytes are. It also shows how far each store is behind its sources and its stale files, from a table bowerbird-byterefs computes weekly.
  • Build records. A config can write sources.meta.tsv, which the stale step compares with a listing. The aad-filelist corpus is a resource a product repo can start from, not a required input. A product whose bytes the project makes can take its signal from its own byte maker, as GHRSST does from cogger. When a store counts as stale is production's decision.

Considerations

  • Keys are immutable to a byte reference. A COG rewritten at the same key invalidates every reference into it: cogger's preliminary-to-final rewrite, a re-encode, a correction. Write each key once, or index only what is final.
  • CRS in the index, not only in the bytes. No published index declares a CRS: there is no <SRS> and no grid_mapping, and the COGs carry theirs. The fix is one re-render, after spec decision 0015 (srs per array) is written.
  • Encoding sets the readers. zstd or DEFLATE without filters reads everywhere. TIFF PREDICTOR=2 and netCDF shuffle are not yet read by GDAL's Zarr readers. Readers of the kerchunk forms through fsspec pass remote_protocol="https".
  • URLs are embedded. grist dsn, STAC hrefs and Icechunk virtual chunk containers name the store's location, so a move rewrites them. Leave pointers behind.
  • source.coop. Production writes need cloud-team Lambda authorization. Temporary keys last an hour and cannot delete, and re-uploads leave Icechunk objects only the dashboard removes.

Not for production yet

Bluelink and ACCESS-ESM1.6 stay with the research team, with production help. So do the publisher-bytes stores (OISST, G02202, AMSR2, ESA CCI ocean colour) and IMOS MEOP. GEBCO is designated for production, but first needs decisions on which grids and releases to carry and on one COG encoding (gebco#2, gebco#4).

How the pieces sit

Bytes, builds and indexes sit in different places; every index points back at its bytes.

Proposed, open to review

One path, one gate

Bytes, file lists and readers are shared. Build and index split into two lanes with a gate between them. The research team owns the lane above the gate, including cleaning up the Nectar, NCI, Pawsey and scratch side. The production team owns the lane below it and sets what a dataset must meet to cross.

What verify checks, and what counts as a failure

  • verify reads the same windows through every rendered form (multidim VRT, kerchunk Parquet through GDAL and, for TIFF predictors, fsspec and zarr, and Icechunk) and compares them with GDAL reading the source files through plan.vrt. Windows per array: the first chunk, one row across every chunk of the last dimension, four random present chunks and one absent chunk. It also checks scale factor and fill value against the sources, and that pyarrow and fastparquet read the same kerchunk paths.
  • verify-published runs the same check on the published copy, read anonymously from source.coop, as a public reader would.
  • verify_grist.py checks grist catalog rows against their source fields, for datasets with a date axis; IBCSO has no grist catalog.
  • A failure is any value that differs (raw values, no tolerance; NaN equals NaN), a wrong scale factor or fill value, or a read error. The script exits 1 and run.sh stops before the next step, so nothing later in that run is published, and publish run on its own finds no verify.json.

Open

Questions to decide together

Decided since 2026-11-06: ownership per product, the four criteria for a move, and the first products (see the brief). The rest are open.

  1. Gate. The four criteria are decided. The process items (product repo, staleness signal, build record, byte layout) are still a proposal, applied to one dataset in IBCSO v2 against the gate.
  2. Product shape. One production product per scratch group (sea ice as one product), one per source, one index product with groups, or stores made location-independent first. The GHRSST index beside its bytes would be the second of these.
  3. Byte layout. One rule for project COGs (IBCSO's <release>/cog/ is the candidate); GEBCO and GHRSST differ today.
  4. Landing pages. One fixed "where things are" block at the top of every product README: bytes, index, where it's built, how to open it.
  5. Runners. Which machine or service runs scheduled production builds, and with which credential. The research team holds every write key in use today; the production team sets the scope and deployment of production keys.
  6. Central refs. Where the collected tables live on source.coop, and whether products keep their own copies.
  7. Moves. Copy the existing indexes or rebuild them; a rebuild gives every dataset the build record the stale check needs. IBCSO and Bedmap3 go first, GHRSST at production's discretion.
  8. After promotion. How production learns that a store is stale, and who acts; how a dataset goes back to the research lane when an upstream format changes; whether a rebuild overwrites the published store or writes a new version beside it (catalog rows embed store URLs, so this decides whether readers' links break); and what to do when "theirs" bytes move or vanish, since their publishers give no availability guarantee.
