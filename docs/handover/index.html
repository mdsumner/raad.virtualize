One path, one gate

Bytes, file lists and readers are shared. Build and index split into two lanes with a gate between them. Michael owns the lane above the gate, including cleaning up the Nectar, NCI, Pawsey and scratch side. The production team owns the lane below it and sets what a dataset must meet to cross.

What verify checks, and what counts as a failure

  • verify reads the same windows through every rendered form (multidim VRT, kerchunk Parquet through GDAL and, for TIFF predictors, fsspec and zarr, and Icechunk) and compares them with GDAL reading the source files through plan.vrt. Windows per array: the first chunk, one row across every chunk of the last dimension, four random present chunks and one absent chunk. It also checks scale factor and fill value against the sources, and that pyarrow and fastparquet read the same kerchunk paths.
  • verify-published runs the same check on the published copy, read anonymously from source.coop, as a public reader would.
  • verify_grist.py checks grist catalog rows against their source fields, for datasets with a date axis; IBCSO has no grist catalog.
  • A failure is any value that differs (raw values, no tolerance; NaN equals NaN), a wrong scale factor or fill value, or a read error. The script exits 1 and run.sh stops before the next step, so nothing later in that run is published.
Credentials

Who writes today

Michael holds every write key today and publishes with source.coop's one-hour product keys, from whichever machine built the index. The production team has source.coop IAM; a scheduled runner gets its own credential (see Runners).

Open

Questions to decide together

None of these is decided.

  1. Gate. What a dataset must meet to move to production (proposed list in the diagram).
  2. Product shape. One production product per scratch group (sea ice as one product), one per source, or one index product with groups.
  3. Byte layout. One rule for project COGs (IBCSO's <release>/cog/ is the candidate); GEBCO and GHRSST differ today.
  4. Landing pages. One fixed "where things are" block at the top of every product README: bytes, index, where it's built, how to open it.
  5. Runners. Which machine or service runs scheduled production builds, and with which credential.
  6. Central refs. Where the collected tables live on source.coop, and whether products keep their own copies.
  7. Moves. Copy the existing indexes or rebuild them; a rebuild gives every dataset the build record the stale check needs. The three pilot datasets go first.
  8. After promotion. Who acts when the stale check fires; how a dataset goes back to the research lane when an upstream format changes; whether a rebuild overwrites the published store or writes a new version beside it (catalog rows embed store URLs, so this decides whether readers' links break); and what to do when "theirs" bytes move or vanish, since their publishers give no availability guarantee.
