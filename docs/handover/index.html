Production handover

We index Southern Ocean and Antarctic array data where it already sits and publish cloud-readable indexes on source.coop, so nobody has to copy the data to read it fast. Each dataset gets one table of byte references (which bytes of which file hold each chunk); the GDAL VRT, kerchunk, Icechunk and STAC forms are all rendered from that table. This page shows how the pieces sit now, how we propose they fit in production, and what is open. Everything marked proposal is for design with the production team, not done.

Now

Three kinds of place

Bytes, work and index are separate places. Some bytes are copies we made (COGs) and host on source.coop or Pawsey object storage; most are left where their publisher puts them. The harvest runs wherever the bytes are fastest to read. The index (a byte-reference table plus the forms rendered from it) is published on source.coop and points back at the bytes, wherever they are.

Why three machines. Nectar is the general build box, near the raad /rdsi mirror, and publishes to source.coop. Gadi is where BRAN lives (/g/data/gb6): scanning it in place is far faster than over THREDDS. Pawsey gives compute for writing our own COGs plus Acacia object storage to host them (about 10.6 TB free). The production question is which of these the team wants to own, and which become a runner they schedule.

Proposed, open to review

Where we see it going: one path, one gate

The same pieces, laid out the way we think they should fit. Bytes, file lists and readers are shared. Build and index split into two lanes with a gate between them. Above the gate, Michael owns the research work: new datasets, engine changes, and cleaning up the Nectar, NCI, Pawsey and scratch complexity. Below the gate, the production team owns scheduled builds and production products. The team sets the requirements a dataset must meet to cross the gate; nothing crosses until those are defined and planned.

Open

Questions to decide together

None of these is decided. Cleaning up the site and scratch side (Nectar, NCI, Pawsey, scratch layout) is Michael's work; these are the production side's calls, to design together.

  1. Gate. What a dataset must meet before it moves to production (the proposed list is in the diagram above).
  2. Product shape. One production product per scratch group (sea ice as one product), one per source, or one index product with groups.
  3. Byte layout. One rule for our own COGs (IBCSO's <release>/cog/ is the candidate); GEBCO and GHRSST differ today.
  4. Landing pages. One fixed "where things are" block at the top of every product README: bytes, index, where it's built, how to open it.
  5. Runners. Which machine or service runs scheduled production builds, and with which credential.
  6. Central refs. Where the collected tables live on source.coop, and whether products keep their own copies.
  7. Moves. Copy the existing indexes or rebuild them; a rebuild gives every dataset the build record the stale check needs.

- what is published for one dataset (ausantarctic/ibcso/virtual/ibcso-v2/)
  and which files record the store's own URL
- what needs credentials, and on which machine each config runs (hpc/)
