The whole picture

Three kinds of place

Bytes, work and index are separate places. Some bytes are copies we made (COGs) and host on source.coop or Pawsey object storage; most are left where their publisher puts them. The harvest runs wherever the bytes are fastest to read. The index (a byte-reference table plus the forms rendered from it) is published on source.coop and points back at the bytes, wherever they are.

Why three machines. Nectar is the general build box, near the raad /rdsi mirror, and publishes to source.coop. Gadi is where BRAN lives (/g/data/gb6): scanning it in place is far faster than over THREDDS. Pawsey gives compute for writing our own COGs plus Acacia object storage to host them (about 10.6 TB free). The production question is which of these the team wants to own, and which become a runner they schedule.

Storage trees

Production product and scratch group, side by side

A scratch group sits where a production product puts virtual/, so datasets are at the same depth. The difference a newcomer meets first is that production mixes bytes and index in one product, while scratch holds index only and its bytes are somewhere else entirely.

Highlighted: the one segment that differs. A move of the index only rewrites the files that record the store's own address (STAC hrefs, grist dsn, catalog self links, public_base, README links). VRT, kerchunk, Icechunk and flat refs point at the bytes and stay as they are.

Proposals, not enacted

Changes to the publications that would make the handover easier

Each of these is a proposal to design with the production team. None of them changes a published store.

Every landing pagesource.coop product READMEs
  • Open with a fixed "Where things are" block, the same on every product (sketch below).
  • Say up front whether the product holds bytes, an index, or both.
  • One link per reader path (GDAL, xarray, R), leading with the form that works in that reader today.
datasets.tsvper product
  • Add columns bytes_at, bytes_owner (ours or theirs), built_on (VM, Gadi, Setonix), corpus_source_id.
  • The landing block, the docs site and this page are then generated from one table instead of written by hand.
raad.virtualize docsmdsumner.github.io/raad.virtualize
  • Replace the "Early runs" table and the AADC transfer bucket text on the overview (both out of date) with this page's whole-picture diagram.
  • Add a "Datasets" page: one card per dataset as above, generated from the datasets.tsv columns.
  • Add a "Where it runs" page: the three sites, their runners and what each builds.
Byte layoutnew production products
  • Agree one rule for our own COGs (IBCSO's <release>/cog/ is the candidate) before more products are made. GEBCO and ghrsst-mur-v2 differ today.
  • Keep bytes and index visibly apart in the tree (virtual/ already does this in production).
Production rootausantarctic/
  • One root catalog linking every production virtual/catalog.json. Scratch has a root catalog; production has none.
